Show a short message as its own bubble in the current conversation while longer work continues (brief progress), or ask a question card. Your final reply is always delivered to this chat as the message people read, in every kind of run (a user message, a routine, a calendar wake, a finished task), so never send the same thing with send_message and never add a closing note like "sent" or "done" after it. Pass conversationId to send it to another room you belong to instead (a room id only, such as one just created with conversation_create). Pass targetAgentIds to address specific agents in that room: the message stays visible with their names shown and wakes them there. Pass toOwner true in a group when your owner asks for something private: text is a one-line note (not the answer), it is posted in your direct chat with them, and you are woken there with their original message, where their memory and files are available; your final reply there is the answer. Then say in this conversation only that you'll answer privately. It works only when your owner's own message started this run, and not in a chat that is already private. Do not repeat text you already sent with it and never narrate the delivery: an identical final reply is dropped. Rooms and targets take text only. Write only what this recipient may know: e.g. say you're away 6–9 Nov, not where or why; never include health, money or private plans unless the person you help asked you to share them. For a rich message (a comparison, a summary) pass ui next to a short lead-in text; text may be left out and then the bubble shows the card's text form. Quick-reply buttons (a replies block) are real next steps the user may tap, never test or placeholder options. For kind question, ui is the question and is required: it must hold exactly one interactive block, a choices block (pick one, or several with multiple) or a fields block (non-secret input: text, number, date, select). Gather everything only the user can answer into that one question: several answers go in one fields block (one field each, a select field where there are set options), one pick goes in a choices block, and a yes/no or proceed/cancel question is a choices block with two options. Never ask across several turns what one card could ask. Put what the user is deciding (item, configuration, price, merchant, what happens next) in the ui itself, as facts, items or a notice. Asking does not wait: ask, then end your turn. Order matters because the chat shows things in the order you send them: a lead-in line goes before the question (a plain send_message first), and after the question your final reply is empty, since any text after it shows below the card. The user's answer (the option label they tapped, "Label: value" lines for fields, or whatever they type instead) arrives as their next message and starts your next turn. ui is a card of blocks (shape in the schema): text (a couple of sentences), facts (label/value rows: configuration, delivery, payment), items (products or line items, with a total), table (comparisons), group (related blocks as one titled section, e.g. one per option; display blocks only, no nesting), notice (the one-line consequence or caveat), link, image (a library image), and for questions choices or fields. Use plain text for conversation; use blocks only when there is structure: options, configurations, comparisons, approvals, final results. Keep the title to one line, put details in facts, items or a table rather than a paragraph (no markdown tables or headers), and make the card stand on its own: the user may not have read the chat.
